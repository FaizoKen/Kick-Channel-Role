Kick Channel Role API

A read-only HTTP API over one Discord server's linked Kick accounts — who has linked, and how they relate to the channels that server has connected (follower, subscriber, VIP, OG, moderator).

Base URL {{BASE_URL}} JSON only Read-only Server-to-server

Overview

Each API key is scoped to exactly one Discord server. That is why no endpoint takes a server ID — the key already carries it. You cannot read a server you weren't given a key for.

The data is the same set the server's own "linked users" page shows: every member of that Discord server who has linked a Kick account, with their relationship to the channels the server has connected. Members who opted out of this plugin are excluded, exactly as they are from role syncing.

This is a server-to-server API. Calls are expected from your backend. Browsers on third-party origins are blocked by CORS, on purpose — it keeps API keys out of frontend bundles, where they'd be public. Never ship a key to a browser, a mobile app, or a public repo.

Get an API key

Keys are created by someone with Manage Server on the Discord server whose data you want. If that isn't you, send these steps to them:

  • Open the RoleLogic dashboard and go to the role using Kick Channel Role.
  • Scroll to API access for other services.
  • Enter a label naming the integration, then Create API key.
  • Copy the token and send it to the developer over a private channel.
The token is shown once. It's stored hashed, so nobody — including the server owner or RoleLogic support — can retrieve it later. Lost it? Create a new key and revoke the old one. Up to 10 live keys per server, which leaves room to rotate without downtime.

A key looks like this — a kck_ prefix and 43 random characters:

kck_yT4nQ2mBv8xKfR1sLpD7wZ0aHcJ9eN3gUiO6bXtVqMk

Authentication

Send the key as a bearer token on every request:

curl -H "Authorization: Bearer $KICK_API_KEY" \
  {{BASE_URL}}/api/v1/whoami
Never put the key in a URL. Query strings end up in server logs, browser history, proxy logs and Referer headers. There is no query-parameter form of this API — the header is the only way.

Revocation is immediate: a revoked key fails on its very next request, with no cached grace period.

Check a key

GET/api/v1/whoamirequires key

Confirms the key works and tells you which server it points at. Make this your first call when wiring up — it turns "something is wrong somewhere" into a clear answer.

{
  "guild": { "id": "918273645509182736", "name": "Faizo's Server" },
  "key":   { "label": "Stream overlay", "scopes": ["users:read"] }
}

guild.name can be null if the name isn't cached yet. That is not an error — the key is still valid.

Get one user

GET/api/v1/users/{discord_id}requires key

Answers "does this specific person qualify?" without paging the whole server. Returns the same user object under a user key.

curl -H "Authorization: Bearer $KICK_API_KEY" \
  {{BASE_URL}}/api/v1/users/273645509182736451
A 404 means "we have nothing to tell you about this person". It deliberately does not distinguish between: not a member of this server, a member who never linked Kick, and a member who opted out. Telling those apart would leak the server's membership list to a key that is only entitled to the linked users.

The user object

FieldTypeMeaning
discord_idstringDiscord snowflake. Always a string — it exceeds 53 bits, so parsing it as a JSON number loses precision.
discord_namestring | nullDisplay name last seen by RoleLogic. May be null.
kick_user_idnumberKick's numeric user ID. Stable across renames — key your records on this, not the username.
kick_usernamestringCurrent Kick username. Can change.
linked_atRFC 3339When they linked their Kick account.
updated_atRFC 3339Last time this record changed. Feed this to updated_since.
relation.is_followerbooleanFollows at least one connected channel.
relation.is_subscriberbooleanHas an active subscription.
relation.is_vipbooleanHolds the VIP badge.
relation.is_ogbooleanHolds the OG badge. Per channel, granted by the broadcaster — not an account-age thing.
relation.is_moderatorbooleanIs a channel moderator.
relation.sub_months_cumulativenumberTotal months subscribed, highest across channels.
relation.sub_streak_monthsnumberCurrent unbroken streak, highest across channels.
relation.gifted_subs_givennumberSubs they have gifted, summed across channels.
relation.followed_atRFC 3339 | nullEarliest follow across channels. null if not following.
relation.last_seen_atRFC 3339 | nullMost recent chat activity seen.
Relations are collapsed across every channel the server has connected. If a server connects two channels and someone subscribes to either, is_subscriber is true. Counts take the highest value (months, streak) or the sum (gifted). You get one row per person, never one per channel.

Pagination

Cursor-based. Keep calling with cursor=page.next_cursor until has_more is false. Results are ordered by an immutable ID, so nobody gets skipped or duplicated if records change while you're paging.

cursor=""
while : ; do
  resp=$(curl -s -H "Authorization: Bearer $KICK_API_KEY" \
    "{{BASE_URL}}/api/v1/users?limit=500&cursor=$cursor")
  echo "$resp" | jq -c '.users[]'
  [ "$(echo "$resp" | jq -r '.page.has_more')" = "true" ] || break
  cursor=$(echo "$resp" | jq -r '.page.next_cursor')
done

Incremental sync

Don't re-download the whole server on a schedule. Record the time before each run, then pass it as updated_since on the next one:

  • Save started_at = now (UTC) before you start paging.
  • Page through with your previous started_at as updated_since.
  • On success, store the new started_at for next time.

Overlap slightly (subtract a minute) rather than trying to be exact — the API is idempotent to read, so seeing a record twice is harmless, while missing one is not.

Deletions are invisible to updated_since. If someone unlinks Kick, leaves the server, or opts out, they simply stop appearing — no tombstone is emitted. Do a full pass (no updated_since) periodically, say daily, and treat anyone missing from it as gone.

Errors

Every error is JSON with an error field describing what happened.

StatusMeaningWhat to do
400A parameter was malformed — a bad updated_since, an unknown relation.Fix the request. Retrying won't help.
401Missing, unknown, or revoked key.Check the header. Ask the server manager whether the key was revoked.
403The key lacks the scope for this endpoint.Have a new key minted.
404No such linked user in this server.Expected and normal. Not an error condition.
429Rate limited.Wait for the Retry-After header (seconds), then retry.
5xxTemporary server-side problem.Retry with exponential backoff.
A 5xx never means "this server has no linked users". If an upstream lookup fails we return an error rather than an empty list, precisely so you can tell the two apart. Treat any non-200 as "no new information" and keep your last good snapshot — do not clear roles, revoke perks, or delete records on a failed poll.

Rate limits

120 requests per minute per key, with a burst of 30. A per-IP limit (5/sec, burst 20) sits underneath and may trip first if you fire a tight burst from one host.

Over the limit you get 429 with a Retry-After header in seconds. Honour it. With limit=500 a single request covers 500 users, so even a large server needs very few calls — if you're hitting the ceiling, raise limit or switch to updated_since rather than polling harder.

Recipes

Node (fetch, built in on 18+)

const BASE = "{{BASE_URL}}/api/v1";
const KEY  = process.env.KICK_API_KEY;

async function allUsers({ updatedSince } = {}) {
  const out = [];
  let cursor = "";
  do {
    const qs = new URLSearchParams({ limit: "500" });
    if (cursor) qs.set("cursor", cursor);
    if (updatedSince) qs.set("updated_since", updatedSince);

    const r = await fetch(`${BASE}/users?${qs}`, {
      headers: { Authorization: `Bearer ${KEY}` },
    });
    if (r.status === 429) {                       // back off and retry
      await new Promise(s => setTimeout(s, (+r.headers.get("retry-after") || 1) * 1000));
      continue;
    }
    if (!r.ok) throw new Error(`${r.status}: ${(await r.json()).error}`);

    const { users, page } = await r.json();
    out.push(...users);
    cursor = page.has_more ? page.next_cursor : "";
  } while (cursor);
  return out;
}

const subs = (await allUsers()).filter(u => u.relation.is_subscriber);
console.log(`${subs.length} subscribers`);

Python (requests)

import os, time, requests

BASE = "{{BASE_URL}}/api/v1"
S = requests.Session()
S.headers["Authorization"] = f"Bearer {os.environ['KICK_API_KEY']}"

def all_users(updated_since=None):
    users, cursor = [], None
    while True:
        params = {"limit": 500}
        if cursor:        params["cursor"] = cursor
        if updated_since: params["updated_since"] = updated_since

        r = S.get(f"{BASE}/users", params=params, timeout=15)
        if r.status_code == 429:
            time.sleep(int(r.headers.get("Retry-After", 1)))
            continue
        r.raise_for_status()

        body = r.json()
        users += body["users"]
        if not body["page"]["has_more"]:
            return users
        cursor = body["page"]["next_cursor"]

print(sum(u["relation"]["is_subscriber"] for u in all_users()), "subscribers")
